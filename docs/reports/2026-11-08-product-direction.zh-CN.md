## 1. 当前项目需要先明确哪件事

**CortexFS 当前文档同时表达了接口层、执行环境和完整 Agent runtime 三种产品范围。** README 的入口定位仍是通过 Linux 文件系统暴露的 Agent runtime；后期架构把模型与会话交还给已有 Agent CLI，同时保留身份、挂载、网络、资源和子进程管理；重建配方则恢复更早的一整套运行时。[S1][S2][S4]

| 材料 | 定义的责任 | 对新定位的影响 |
| --- | --- | --- |
| README | 通过 Linux 文件系统暴露的 Agent runtime | 项目入口仍承诺运行时产品 |
| 后期架构文档 | Agent CLI 自管模型、工具循环、审批、会话和上下文；CortexFS 管理执行边界和 FUSE | 执行治理与文件系统接口并存 |
| 早期重建配方 | 重建模型、Agent、会话、通道、SDK、CLI、安装和文档体验 | 全量恢复配方会恢复较大的产品范围 |

**当前主分支是文档、ABI 合同与重建配方仓库。** 产品源码、安装器、测试与文档网站实现已经移除；现有 Git 子模块没有接回 CortexFS 产品实现。因此，本稿不以功能清单推算完成百分比，下一版的实现与验收应基于新目标单独建立。[S1][S11]

**最关键的产品决定是 CortexFS 是否负责运行 Agent。** 现有内部架构已经规定 FUSE 层只依赖基础对象与路径合同，独立于执行编排和 CLI。这为专注文件接口提供了现成的分层依据。[S3]

## 2. 推荐定位：给现有程序使用的能力文件系统

> **CortexFS 把外部资源、工具说明和调用结果挂载成可浏览的 Linux 文件接口，让已有 Agent、脚本和开发工具按路径发现、读取和使用这些能力。**

**“能力”在这里指具有明确输入、结果与权限的外部操作。** 例如查询一次 CI 运行、读取一段构建日志，或调用一个已有工具服务。核心产品负责让这些对象可以被发现和访问；外部程序负责选择下一步做什么。

**首批使用者建议聚焦于 Linux 上组合现有 Agent 与外部工具的开发者。** 他们已经有 Agent、脚本和服务，新增一个服务时却需要在不同消费端重复接入。CortexFS 的产品假设是：一份稳定的文件视图，可以被现有文件工具和多个消费端复用，从而减少这些重复工作。

**技术核心保持通用，第一批体验聚焦 Agent 工具接入。** 核心只认识路径、对象、读取、权限、版本和错误；MCP、HTTP API、已有 CLI 和运行时观测数据通过适配器接入。模型名称、会话格式、上下文压缩策略等业务逻辑归属于对应外部程序。

**建议使用直接描述作用的对外文案：**“把工具与资源挂载到 Linux 文件树。”技术说明再补充 FUSE、适配器和对象接口。性能、可靠性与接入成本的效果，需要下面的实验给出依据。

## 3. 先选一个核心体验

| 方向 | 用户首次使用时完成什么 | 主要工程成本 | 建议 |
| --- | --- | --- | --- |
| **A. 外部资源与工具的文件接口** | 现有 Agent 和脚本浏览资源、读取结果，并通过显式入口调用工具 | 适配器、稳定命名、缓存、读取与调用语义 | **优先验证** |
| B. Agent 状态观察窗口 | 查看运行时主动暴露的上下文、工具事件与会话状态 | 上游观测集成、来源标识、完整性说明 | 作为具体适配器用例 |
| C. 通用服务数据挂载 | 编辑器、脚本等按路径访问多种远端服务的数据 | 服务语义、分页、认证、更新与缓存差异 | 在首个用例成立后考虑 |

**选择 A 的理由是它能利用已有 Agent，同时把产品边界维持在接口层。** B 的主要困难是从上游取得真实运行事实：FUSE 只能呈现上游提供的数据；C 的服务范围过宽，容易在证明用户收益前承担大量适配工作。这些判断是设计取舍，并非现有实验结果。

**“统一接口”只覆盖发现和访问机制。** 不同工具的输入参数、业务含义和结果格式仍由各自 schema 定义。一个查询构建日志的工具与一个图像处理工具，不会因为都出现在目录中就获得相同业务语义。

### 体验草图

以下路径仅说明拟议体验，尚未成为新 ABI。目录示例沿用当前八项根目录中的 `tool/` 与 `shared/`；正式路径合同需要在产品方向确定后写入版本化规范。[S2][S10]

| 拟议路径 | 用户获得什么 |
| --- | --- |
| `/ctx/tool/ci.d/description` | 工具用途 |
| `/ctx/tool/ci.d/schema` | 输入参数说明 |
| `/ctx/shared/ci/project/run-42/meta.json` | 某次运行的状态、commit、来源和抓取时间 |
| `/ctx/shared/ci/project/run-42/jobs/build/log.txt` | 某个 job 的日志 |
| `/ctx/tool/ci` | 后续按明确调用合同提供的薄执行入口 |

拟议读体验：

```sh
cat /ctx/shared/ci/project/run-42/meta.json
rg -n 'error|failed' /ctx/shared/ci/project/run-42/jobs
```

**这一体验的目标是让现有文件工具直接工作。** 第一轮原型只验证只读资源；动作调用是独立的下一项产品决定。若需要图形界面，它可作为同一对象视图的薄客户端，主要显示来源、状态、说明和结果。

## 4. 为什么值得用文件系统

**FUSE 的直接价值是路径兼容性。** 既有程序已经会打开文件、遍历目录和读取内容，挂载层可以把外部数据接到这些程序已经理解的入口上。对于需要动态内容、材料量大但访问稀疏、多个消费端复用同一视图的场景，这可能比每个消费端单独接入更省事。

**现成工具已经提供了强基线。** GitHub CLI 支持失败日志、结构化 JSON 与 jq 过滤；MCP 定义资源发现和读取，以及带 schema 的工具发现和调用；rclone 支持把远端存储挂载为文件系统；AgentFS 已有基于 SQLite 的文件、状态与工具调用记录，并提供 Linux FUSE 挂载。[S5][S6][S7][S8][S9]

| 现有方案 | 已有能力 | CortexFS 需要证明的额外收益 |
| --- | --- | --- |
| 现成 CLI / API | 直接查询服务并输出可处理的数据 | 统一视图对多个消费端的复用收益 |
| MCP | 资源与工具的发现、读取和调用 | 只理解文件路径的消费端可以实际使用这些能力 |
| 普通目录导出 | 稳定文件布局，可供搜索、编辑器与脚本读取 | 按需加载、持续更新或规模上的明确收益 |
| rclone | 远端存储挂载和 VFS 缓存 | 面向服务对象及操作结果的具体使用价值 |
| AgentFS | Agent 状态、文件和调用记录的存储与访问 | 投影既有外部系统，保持其事实来源和存储归属 |

**最强的反例是一个简单导出脚本已经足够。** 如果资料很少、变化慢，或者原生 CLI/MCP 已经服务好所有消费端，新增挂载、缓存和一致性机制会增加维护成本。新定位要主动接受这个反例，并通过对照实验寻找实际需要动态文件视图的场景。

## 5. 核心职责怎样收敛

| 所在位置 | 负责的事情 | 这样划分的目的 |
| --- | --- | --- |
| CortexFS 核心 | 命名与发现、目录和文件投影、读取版本、经挂载访问的权限检查、错误表达 | 让所有适配器遵守同一文件接口 |
| 适配器 | 外部协议、认证衔接、分页、资源映射、明确授权的调用、来源信息 | 把不同服务的差异留在边界 |
| 可选薄调用入口 | 把一次明确请求交给适配器，返回结果和退出状态 | 复用已有执行协议，维持小接口 |
| 已有 Agent / 脚本 | 模型选择、提示词、会话、工具选择与任务循环 | 复用使用者已经选择的工作方式 |
| 宿主执行环境 | 进程启动、完整的目录和网络隔离、资源限制与生命周期 | 由真正控制进程的边界承担这些保证 |

**文件权限的承诺应覆盖经过该挂载的访问。** 进程还能接触哪些其他目录、网络和 socket，由宿主执行环境约束；当前架构把这些职责放在执行层，收敛后的产品说明也应保留清楚的归属。[S2][S3]

**底层数据来源可以替换。** 核心协议表达对象及其可见行为；普通文件、外部 API 或某种持久存储均可成为来源。现有 FUSE 规范本就区分 ABI 视图与后端，这一原则值得保留。[S12]

**现行八项根目录只构成当前兼容合同。** 新定位不会要求为了填满历史目录而恢复全部子系统。后续若改变路径或能力含义，需要明确新旧版本的对应关系；本讨论稿保持现有规范与固定配方的含义。

## 6. 文件读取与动作调用要分别设计

### 6.1 可以反复读取的资源

**浏览与读取只表达观察意图。** `ls`、`stat`、`cat`、`rg` 可以产生受控的远端取数，但不会隐含启动模型、重跑 CI 或创建外部对象。读取有流量、速率限制和缓存成本，这些成本应可以看见。

**同一次打开应读到一致的内容版本。** 当后端更新时，分块读取 JSON 不能混合两代内容。资源附带来源、版本或抓取时间；旧数据和不可用状态应能够区分。跨文件的一致快照只有在明确声明的范围内才成立。

**按需加载需要与可控请求量一起设计。** 扫描目录本身不应无界下载整套远端内容；读取被选中的文件时，适配器根据后端能力选择按块读取或一次取回并缓存。分页、目录数量、超时和不支持的操作要有明确行为。全目录搜索仍可能访问大量数据，实验应记录这一代价。[S8]

### 6.2 明确发起的动作

**工具调用需要一次明确的提交语义。** 如果后续确实需要从文件界面发起外部操作，应定义输入校验、请求标识、提交点、状态、结果和错误。普通读取不触发动作；普通文件 `write/close` 也不能直接承担“恰好执行一次”的保证。

libfuse 的官方接口文档说明，`flush` 对同一次打开可能多次调用，也可能不调用；`release` 的返回值会被忽略。把这些回调直接视作唯一业务提交点会丢失必要的调用语义。[S13]

**建议优先采用已有对象执行入口或薄客户端加适配器传输。** 当前对象 ABI 已区分可执行入口、控制目录和可选 socket。执行入口需要真实程序或可执行 shim，FUSE 不会因为文件带执行位就提供一个自动的远端调用回调。shim 属于适配器配套入口；适配器负责一次调用的通信与结果归属，Agent loop 与进程编排留在消费端及宿主环境。[S10][S13]

**重试保证必须受上游能力约束。** 同一请求 ID 可以帮助本地去重，但网络中断后若上游缺少幂等支持，结果可能处于待核实状态。首个实验验证只读任务，把有副作用操作的合同留给实际需要它的下一项切片。

## 7. 最小验证闭环

### 任务与样本

**建议用“解释某次 CI 为什么失败，并引用对应 commit 和日志”作为首个真实任务。** 这个任务有明确结果、真实资料和现成 CLI 基线；它的用途是验证接口收益，而非宣布 CI 查询本身是新能力。[S5]

建议选取自有仓库约 10 个已人工确认原因、具有完整日志的已结束运行。这个数量是初步实验规模建议，尚未执行。固定 run ID、attempt、commit、日志与参考答案；在线实验另记录各数据源的版本或抓取时间。

首个适配器只需要 runs 元数据、job 元数据、日志和来源信息。它可以复用已有 CLI 或 API 客户端，避免为演示重新建设整个外部平台接入栈。

### 三路对照

| 路径 | 要回答的问题 |
| --- | --- |
| 直接使用 `gh` | 现成工具能否已经很好完成任务？ |
| 导出相同结构的普通目录 | 统一资料布局本身能带来多少收益？ |
| CortexFS 按需挂载相同资料 | FUSE 比普通目录多带来什么？ |

**三路对照使用相同事实、任务和权限。** 若参与者是 Agent，固定模型、提示词预算与可用工具范围，并记录实际请求；若存在随机输出，做配对重复，保留每次原始结果，避免用单次成功作结论。静态样本检验正确性，受控更新场景检验新鲜度，两者分开报告。

**这轮对照的结论限定于 GitHub CLI 和普通目录。** 若首批消费端主要通过 MCP 接入工具，下一轮应增加直接 MCP 调用基线，再评价相对 MCP 的收益。

**评价同时覆盖收益和新增成本。** 记录定位正确率、引用正确率、首次配置时间、任务完成时间、专用接入代码量、传入模型的数据量、远端请求数、读取字节、冷暖缓存耗时和故障定位时间。实验开始前固定判断标准，不预填节省比例或性能结果。

### 继续投入与收窄条件

| 观察结果 | 后续决策 |
| --- | --- |
| 挂载在明确的动态或稀疏读取场景中降低成本，且正确性与新鲜度达标 | 继续验证第二个真实数据源 |
| 普通目录已获得相同体验与成本收益 | 保留布局与适配器成果，重新评估 FUSE 是否值得作为产品核心 |
| 原生 CLI/MCP 同样顺畅，挂载仅增加维护 | 收窄到确实依赖文件路径的消费端 |
| 新数据源要求核心新增服务专属分支 | 修改接口与适配边界后再扩展 |
| 最小用例需要重新引入模型路由、会话或任务编排 | 重新检查范围与职责划分 |

**本轮结果是可评审的定位与实验设计。** 本轮未恢复产品源码、执行 FUSE 挂载、进行三路对照或测试真实模型；以上指标均为拟议评价方法。

## 8. 接下来与使用者讨论什么

**首先讨论用户装好 CortexFS 后，第一件想完成的事情。** 三种回答对应不同的产品优先级：

- “让已有 Agent 和 shell 用上原本难接入的外部资源与工具。”对应方向 A。
- “看清 Agent 这一步实际读了什么、收到了什么、调用了什么。”对应方向 B。
- “让我已有的文件工具访问远端服务数据。”对应方向 C。

**第二个决定是首版是否必须发起动作。** 若只读资源已经解决问题，先验证读取；若核心体验必须调用工具，就同时明确真实调用入口及结果语义。文件写入触发动作是否是必要交互，也应由具体任务来决定。

**第三个决定是第一个愿意天天使用的真实工作流。** CI 排错是本稿推荐的试验任务。若另一个现有工作流的接入痛点更明确，应让实验围绕那个工作流展开。
