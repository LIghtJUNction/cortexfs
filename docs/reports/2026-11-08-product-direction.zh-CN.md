## 2. 建议讨论的产品定义

> CortexFS 把外部资源、工具说明和调用结果挂载为可浏览的 Linux 文件接口，让已有 Agent、脚本和开发工具按路径发现、读取和使用这些能力。

这里的“能力”指一个有明确输入、结果和权限的外部操作。模型如何思考、会话如何维护、进程如何隔离，分别由使用 CortexFS 的程序和宿主执行环境负责。

首批使用者建议聚焦于在 Linux 上组合现有 Agent 和外部工具的开发者。需要验证的核心任务是：让同一套文件操作和脚本处理原本分散于外部服务的资料，减少每个消费端重复编写接入逻辑的工作。

该收益当前属于产品假设。统一发现方式不会自动统一不同服务的业务语义，工具参数及输出格式仍需由各自 schema 说明。

## 3. 三种可选方向

| 方向 | 用户首先完成什么 | 主要成本 | 当前建议 |
| --- | --- | --- | --- |
| 能力文件系统 | 已有 Agent 或脚本发现外部资源、读取结果、显式调用工具 | 适配器、稳定路径、读写与调用语义 | 优先验证 |
| Agent 观察文件系统 | 查看 Agent 主动暴露的上下文、工具事件和会话状态 | 各运行时提供观测数据，维护数据来源与完整性 | 可作为适配器用例 |
| 通用服务文件系统 | 用文件路径访问大量远端服务的数据 | 服务间语义差异、分页、缓存、更新与认证 | 待首个用例验证后再决定扩展 |

首版应选择一个使用场景。三种方向全部并行会让相同目录承担不同产品承诺。

## 4. 必须回答的验证问题

GitHub CLI 已有失败日志读取、JSON 输出和 jq 过滤能力。检查 CI 可以成为一个真实验收任务，但单凭这个任务不能形成 CortexFS 的独立优势。[S5]

建议比较同一组任务的三种实现：

1. 直接使用现成 CLI 或 API。
2. 把相同资料导出成普通目录。
3. 使用 CortexFS 按需挂载相同资料。

比较任务正确率、接入代码与时间、实际远程请求、读取字节、冷暖启动耗时、数据新鲜度和排错时间。以同一数据范围、同一错误注入和相同权限进行对照。若普通目录已经满足需求，应优先保留简单方案；若按需读取、持续更新或既有软件兼容性带来明确收益，再投入 FUSE 产品实现。

本轮没有恢复产品源码或执行上述实验，所有效果判断均待验证。
